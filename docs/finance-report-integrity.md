# قرارداد اصلاح گزارش مالی و ثبت معکوس

تاریخ: ۲۶ آبان ۱۴۰۵ / ۱۷ نوامبر ۲۰۲۶. migration پیشنهادی: `20261117000015_finance_report_integrity.sql`؛ **تا بازبینی، ادغام و نصب، قابل اتکا به‌عنوان قرارداد نصب‌شده نیست.**

## مسئله و تعریف ارقام

صفحهٔ گزارش هستی (#56 و #61) پرداخت مثبتِ معکوس‌شده را در «تعداد» نمی‌شمارد، ولی تابع قبلی همهٔ ردیف‌ها را می‌شمرد. مثال: ۱۰۰ هزار، معکوس ۱۰۰ هزار و پرداخت سالم ۲۰۰ هزار باید جمع ۲۰۰ هزار، تعداد ۱ و میانگین ۲۰۰ هزار بدهد.

- جمع خالص: جمع همهٔ مبالغ در بازه، شامل ثبت معکوس و برگشت پول مستقل.
- تعداد: فقط مبلغ مثبت با `reverses_payment_id=null` که هیچ ردیفی آن را معکوس نکرده باشد. ردیف معکوس و برگشت پول شمرده نمی‌شوند.
- میانگین: جمع خالص / تعداد؛ اگر تعداد صفر است، صفر. گردکردن مانند `Math.round` رابط است؛ برای منفیِ نیمه نیز به سمت مثبت می‌رود (مثلاً ‎−۱٫۵ → ‎−۱).
- همین تعریف تعداد در تفکیک روش، بیمه و روز اعمال می‌شود. گروهی که جمع و تعدادش هر دو صفر است از تفکیک روش/بیمه حذف می‌شود؛ روش یا بیمهٔ غیرفعال از سابقه حذف نمی‌شود.
- هر دو سر بازه شامل‌اند و مرز روز `Asia/Tehran` است؛ مبنا `paid_at` است، نه `created_at`. آرایهٔ روزانه همهٔ روزهای بازه، حتی روز بدون پرداخت، را دارد. تاریخ خالی یا بازهٔ وارونه با `22023` رد می‌شود.

## نگاشت برای هستی

نام تابع و ورودی‌ها همان `finance_report(p_from, p_to)` و نوع خروجی همان JSON است. کلیدهای قبلی حذف نشده‌اند. `id` و `count` به تفکیک‌ها اضافه شده؛ روزانه نیز `count` دارد.

| خروجی RPC | نوع صفحهٔ گزارش |
|---|---|
| `net_total` | `netToman` |
| `count` | `count` |
| `average` | `averageToman` |
| `by_method[].{id,total,count}` | `byMethod[].{id,totalToman,count}` |
| `by_insurance[].{id,total,count}` | `byInsurance[].{id,totalToman,count}` |
| `daily[].{day,total,count}` | `daily[].{dayKey,totalToman,count}` |

`name` در تفکیک‌ها همچنان موجود است؛ شناسهٔ بیمهٔ خالی `null` و نام نمایشی «بدون بیمه» است. تفکیک‌ها نزولی بر مبنای جمع و روزها صعودی‌اند. برای جمع یکسان، ترتیب نام/شناسه قطعی است؛ روی ترتیب قبلی دادهٔ نمونه تکیه نشود.

خواندن با نشست خود پزشک از فایل سمت سرور انجام شود. منشی به این تابع راه ندارد. هستی پس از اعلام **نصب**، جمع‌ها و تفکیک‌های گزارش را از آن بگیرد؛ نمودارها/جزئیات دیگری مانند ساعت شلوغی یا فهرست اصلاحات که در این خروجی نیستند، با این migration به RPC منتقل نمی‌شوند. فایل‌های ماژول مالی در این PR تغییر نمی‌کنند.

## کنترل ثبت معکوس در دیتابیس

طبق تصمیم 0010، منشی فقط پرداخت امروز تهران را معکوس می‌کند. `check_payment_reversal` قبلاً SECURITY DEFINER بود و ردیف پنهان از RLS را می‌دید؛ تکیه بر اینکه action ردیف دیروز را پیدا نمی‌کند، برای مسیر مستقیم INSERT کافی نبود.

کنترل تازه با نقش نشست (`current_app_role()`)، روز پرداخت اصلی را بررسی می‌کند و برای منشی روزهای قبل **و آینده** را با `42501` رد می‌کند. پزشک همچنان پرداخت قدیمی را معکوس می‌کند. این کنترل به `recorded_by` ارسالی اعتماد نمی‌کند. کنترل مبلغ، روش، مراجع، بیمه، تاریخ، منع زنجیره و یکتایی معکوس قبلی حفظ می‌شوند. درج پرداخت عادی یا برگشت پول مستقل از این تغییر متأثر نیست.

نگاشت خطای فعلی #61 برای `42501` پیام فارسی «اجازهٔ این کار را ندارید» دارد؛ رفتار دوستانهٔ action برای پرداخت غیرامروز نیز باقی می‌ماند. تغییر جدید هیچ ردیف مالی را ویرایش یا پاک نمی‌کند و مجوزهای اجرای تابع‌ها را عوض نمی‌کند.

## آزمون و انتشار

```powershell
node --env-file=.env.local supabase/tests/run-finance-integrity.mjs --check
node --env-file=.env.local supabase/tests/run-finance-integrity.mjs
```

در صورت نبود CLI در PATH، `--cli <path-to-supabase>` بدهید. آزمون، migration و داده‌های ساختگی را در یک تراکنش اجرا می‌کند و در پایان عمداً همه را برمی‌گرداند؛ اجرای موفق به معنی نصب نیست. برای آزمون از پایگاه آزمون استفاده شود؛ تغییر موقت تابع‌ها قفل کوتاه‌مدت می‌گیرد. مقدار رازها و خروجی خام CLI چاپ نمی‌شوند.

پس از بازبینی عضو دیگر و ادغام، سعید migration را نصب و سپس خبر اتصال را به هستی می‌دهد. آزمون مرورگری ثبت/تازه‌کردن صفحه/معکوس/معکوس دوباره و دسترسی پزشک/منشی در #61 هنوز جداگانه لازم است. در محیط مشترک، ثبت معکوس فقط جمع را خنثی می‌کند و ردیف آزمون را حذف نمی‌کند.

## نتیجهٔ بررسی ۲۶ آبان

۱۹ آزمون SQL موفق شد: جمع/تعداد/میانگین با ثبت معکوس و برگشت پول، گروه صفر، بیمهٔ غیرفعال و بدون بیمه، مرز نیمه‌شب تهران، بازهٔ خالی و نامعتبر، میانگین منفی، RLS منشی، رد INSERT مستقیم معکوس دیروز/فردا، پذیرش معکوس امروز، رد معکوس دوباره، منع گزارش برای منشی/ناشناس، اجازهٔ پزشک برای اصلاح دیروز و حفظ کنترل مبلغ قرینه. تراکنش در پایان عمداً برگشت؛ migration نصب نشد. lint و build شامل TypeScript نیز موفق بودند. هشدار قبلی `CRON_SECRET` باقی است؛ نسخهٔ Next.js در این PR ارتقا نیافته است.

بررسی مستقل پس از آزمون: شمار پرداخت‌ها قبل و بعد ۱۸ بود و اثرانگشت بدنهٔ هر دو تابع با قبل برابر ماند؛ تغییر آزمون روی پایگاه نصب نشده است.
