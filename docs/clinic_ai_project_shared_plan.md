## ۱. هدف پروژه

طراحی و پیاده‌سازی تدریجی یک سامانه یکپارچه برای پشتیبانی از امور اجرایی و مالی یک مطب پزشک متخصص طب فیزیکی و توان‌بخشی، با رویکرد آموزشی و استفاده از ابزارهای هوش مصنوعی برای کمک به توسعه نرم‌افزار (Vibe Coding).

تمرکز نسخه اولیه بر **امور اداری، نوبت‌دهی و مالی** است؛ نه نگهداری یا پردازش پرونده پزشکی و اطلاعات بالینی بیماران.

### اهداف اصلی
- یکپارچه‌کردن بخشی از فرایندهای پراکنده مطب
- کاهش کار دستی و فراموش‌شدن پیگیری‌ها
- فراهم‌کردن امکان توسعه مرحله‌ای و کم‌هزینه
- یادگیری کار تیمی با GitHub و Claude Code
- آماده‌سازی زیرساختی که در صورت موفقیت نسخه آموزشی، قابلیت توسعه داشته باشد

## ۲. وضعیت فعلی مطب و نیازهای شناسایی‌شده

بر اساس اطلاعات مطرح‌شده تا این مرحله:

- مطب در ایران فعالیت می‌کند.
- تعداد مراجعه‌ها کمتر از ۲۰ مراجعه در روز است.
- نوبت‌دهی و ارتباط با مراجعان از راه‌هایی مانند تلفن، مراجعه حضوری و پیام‌رسان‌ها انجام می‌شود.
- اطلاعات در دفترها و فایل‌های مختلف ثبت می‌شوند و نرم‌افزار یکپارچه‌ای برای مطب وجود ندارد.
- هدف، یکپارچه‌سازی تدریجی امور اجرایی مطب است.
- اطلاعات پرداخت در مرحله اول می‌تواند به‌صورت دستی ثبت شود و سپس برای تهیه گزارش‌های مالی استفاده شود.
- دسترسی به داده‌های بازخورد و نظرات مراجعان هنوز مشخص نشده است.
- ترکیب دقیق کانال‌های ارتباطی فعلی هنوز نهایی نشده است.

## ۳. قابلیت‌های مدنظر

این موارد، چشم‌انداز کلی پروژه‌اند و قرار نیست همگی در نسخه اول ساخته شوند.

1. **وب‌سایت مطب**
   - معرفی پزشک و خدمات
   - اطلاعات تماس و راهنمای مراجعه
   - امکان درخواست یا ثبت نوبت آنلاین

2. **مدیریت نوبت‌ها**
   - ثبت و مشاهده نوبت‌ها
   - مدیریت وضعیت نوبت
   - بررسی تداخل زمانی و جلوگیری از ثبت نوبت‌های هم‌پوشان
   - امکان توسعه یادآوری نوبت‌ها در مراحل بعد

3. **مدیریت اداری مراجعان**
   - ثبت حداقل اطلاعات لازم برای امور اجرایی
   - جست‌وجو و مشاهده سوابق اداری مجاز
   - پرهیز از جمع‌آوری اطلاعات غیرضروری

4. **پنل مالی**
   - ثبت دستی پرداخت‌ها
   - تهیه گزارش‌های پایه مالی
   - امکان تطبیق گزارش‌ها با داده‌های ثبت‌شده

5. **چت‌بات پرسش‌های پرتکرار**
   - پاسخ به پرسش‌های عمومی درباره خدمات، ساعات کاری، نشانی، نحوه نوبت‌گیری و موارد مشابه
   - شروع با پاسخ‌های ازپیش‌تعریف‌شده و تأییدشده
   - خودداری از تشخیص، توصیه درمانی یا پاسخ‌گویی بالینی

6. **یادآوری نوبت‌ها**
   - قابلیت توسعه در مرحله بعد
   - انتخاب کانال و ارائه‌دهنده پس از بررسی دسترسی، هزینه و محدودیت‌های فنی

7. **ربات تلگرام و دستیار اینستاگرام**
   - قابلیت‌های احتمالی مراحل بعد
   - وابسته به دسترسی رسمی، محدودیت‌های پلتفرم و هزینه‌های احتمالی
   - جزئیات و اولویت هر کانال هنوز مشخص نشده است

8. **داشبورد بازخورد و نظرات**
   - تحلیل بازخوردها و گزارش‌های مدیریتی
   - اجرای این بخش منوط به مشخص‌شدن منبع و امکان دسترسی مجاز به داده‌هاست

## ۵. پیشنهاد فنی اولیه

پیشنهاد فعلی، انتخاب یک مسیر ساده و یکپارچه برای یادگیری است؛ نه ساخت معماری پیچیده از ابتدا.

### فناوری‌های پیشنهادی

| بخش | پیشنهاد | دلیل انتخاب |
|---|---|---|
| رابط کاربری و برنامه اصلی | Next.js + TypeScript | امکان ساخت صفحات وب، پنل مدیریت و بخش‌های سمت سرور در یک پروژه |
| پایگاه داده | PostgreSQL از طریق Supabase | پایگاه داده رابطه‌ای و مدیریت‌شده؛ مناسب داده‌های نوبت و پرداخت |
| احراز هویت | Supabase Auth، در صورت نیاز | کاهش کار لازم برای پیاده‌سازی ورود کاربران |
| میزبانی و انتشار | Vercel | مسیر ساده برای انتشار پروژه Next.js |
| همکاری تیمی و کنترل نسخه | GitHub | نگهداری کد، شاخه‌های جداگانه و بازبینی تغییرات |
| دستیار توسعه | Claude Code | کمک به نوشتن، توضیح، اصلاح و آزمون کد؛ با بازبینی انسانی |

**معماری پیشنهادی در سطح کلی:**

رایانه هر عضو + Claude Code → مخزن GitHub → استقرار برنامه در Vercel → پایگاه داده و خدمات احراز هویت در Supabase

این معماری اولیه است. جزئیات امنیت، دسترسی‌ها، ساختار داده و تنظیمات انتشار باید پیش از استفاده واقعی طراحی و بررسی شوند.

### گزینه‌های دیگری که مطرح شدند

- **React همراه با بک‌اند جداگانه:** انعطاف‌پذیر است، اما برای تیم مبتدی دو بخش و دو مسیر اجرایی ایجاد می‌کند.
- **Django:** گزینه‌ای معتبر برای برنامه‌های داده‌محور است، اما در این پروژه با توجه به انتخاب اولیه Claude Code و مسیر یکپارچه وب، فعلاً پیشنهاد اول نیست.
- **Firebase:** می‌تواند برای برخی کاربردها مناسب باشد، اما نیازهای داده‌ای این پروژه به مدل رابطه‌ای نوبت‌ها و پرداخت‌ها نزدیک است.
- **Neon:** گزینه‌ای برای میزبانی PostgreSQL است؛ ولی برای شروع ممکن است به تنظیم و اتصال خدمات جانبی بیشتری نیاز باشد.
- **SQLite محلی:** برای تمرین یا نمونه بسیار ساده مناسب است، اما انتخاب اول برای نسخه آنلاین چندکاربره نیست.
- **ابزارهای بدون کدنویسی یا کم‌کد:** ممکن است شروع را آسان کنند، اما در این پروژه هدف یادگیری همکاری تیمی و توسعه با کد نیز هست.

این مقایسه، تصمیم اولیه است؛ پیش از انتخاب نهایی باید محدودیت‌ها و شرایط روز سرویس‌ها بررسی شود.

## ۶. هزینه و محدودیت طرح‌های رایگان

هدف، شروع با حداقل هزینه و استفاده از طرح‌های رایگان در صورت امکان است؛ اما **رایگان‌بودن دائمی یا مناسب‌بودن طرح رایگان برای استفاده واقعی تضمین‌شده نیست**.

مواردی که باید پیش از انتشار بررسی شوند:

- سقف مصرف، فضای ذخیره‌سازی و منابع در Supabase
- محدودیت‌های میزبانی و استفاده مجاز از Vercel Hobby
- احتمال توقف یا محدودشدن سرویس‌های رایگان پس از عدم فعالیت
- محدودیت منطقه‌ای، احراز هویت، پرداخت و دسترسی به سرویس‌ها از محل فعالیت
- هزینه احتمالی API مدل‌های هوش مصنوعی، پیامک و سرویس‌های پیام‌رسان
- محدودیت‌های رسمی تلگرام و اینستاگرام و دسترسی به APIهای مربوط
- هزینه و امکان تهیه نسخه پشتیبان و بازیابی اطلاعات

در نتیجه، پیش از هر تعهد مالی یا استفاده عملیاتی، قیمت‌ها، شرایط و دسترسی هر سرویس باید در وب‌سایت رسمی آن بررسی شوند. در صورت نیاز به کاهش هزینه، ابتدا قابلیت‌های اصلی را با داده‌های ساختگی و بدون API پولی بسازید.

## ۸. قواعد همکاری با GitHub

### قاعده اصلی
**هیچ عضوی مستقیماً روی شاخه `main` کار نکند یا تغییرات را بدون بازبینی در آن ادغام نکند.**

### چرخه کاری پیشنهادی

1. آخرین تغییرات شاخه `main` را دریافت کنید.
2. برای یک کار مشخص شاخه جدید بسازید.
3. با کمک Claude Code فقط همان کار را انجام دهید.
4. تغییرات را اجرا و بررسی کنید.
5. یک commit با پیام روشن ثبت کنید.
6. Pull Request (PR) باز کنید.
7. عضو دیگر تغییرات را بررسی کند.
8. پس از رفع ایرادها، تغییرات ادغام شوند.

### نمونه نام شاخه‌ها

- `feature/appointment-form`
- `feature/patient-list`
- `feature/payment-report`
- `feature/faq-chatbot`
- `fix/appointment-conflict`
- `docs/setup-guide`

هر شاخه بهتر است یک هدف روشن و محدود داشته باشد. اگر تغییرات یک عضو باعث خراب‌شدن اجرای پروژه شد، ادغام تغییرات بعدی تا رفع مشکل متوقف شود.

- هدف پروژه و محدوده نسخه فعلی
- فناوری‌های مصوب و ساختار پوشه‌ها
- قراردادهای نام‌گذاری و سبک کدنویسی
- روش اجرای برنامه و آزمون‌ها
- ممنوعیت افزودن قابلیت خارج از محدوده بدون توافق تیم
- ممنوعیت قراردادن کلیدها و رمزها در کد یا مخزن
- استفاده از داده‌های کاملاً ساختگی در توسعه و آزمون
- درخواست توضیح تغییرات به زبان ساده برای اعضای مبتدی
- اعلام فایل‌های تغییرکرده، دستورات اجراشده، نتایج آزمون و موارد حل‌نشده
- پرهیز از بازنویسی گسترده کدهای نامرتبط با کار جاری

Claude Code دستیار توسعه است، نه جایگزین بازبینی اعضای تیم. خروجی تولیدشده باید بررسی، اجرا و آزمون شود.

## ۱۰. امنیت، محرمانگی و داده‌ها

در مرحله آموزشی:

- از نام، شماره تلفن، اطلاعات مالی یا هرگونه اطلاعات واقعی مراجعان استفاده نکنید.
- پرونده پزشکی و اطلاعات بالینی خارج از محدوده نسخه اولیه است.
- فایل `.env` باید محلی بماند و در `.gitignore` قرار گیرد.
- فقط نام متغیرها و مقدارهای خالی یا نمونه در `.env.example` ثبت شوند.
- کلید API، رمز عبور، توکن ربات یا اطلاعات اتصال پایگاه داده را در GitHub، پیام‌های عمومی یا اسکرین‌شات‌ها منتشر نکنید.
- اگر کلیدی افشا شد، آن را افشاشده فرض کنید و تعویض/لغو کنید.
- دسترسی کاربران به داده‌ها باید از ابتدا طراحی شود؛ مخفی‌کردن یک صفحه در رابط کاربری به‌تنهایی کنترل دسترسی محسوب نمی‌شود.
- پیش از استفاده واقعی در مطب، امنیت، پشتیبان‌گیری، بازیابی، محرمانگی، الزامات قانونی و مسئولیت‌های عملیاتی باید جداگانه بررسی شوند.

نسخه اولیه دست‌کم باید با داده‌های ساختگی این موارد را بررسی کند:

- ثبت و مشاهده نوبت
- جلوگیری از ثبت نوبت‌های هم‌پوشان
- ثبت پرداخت دستی
- نمایش گزارش مالی پایه بر اساس داده‌های ثبت‌شده
- محدودبودن دسترسی صفحات مدیریتی به کاربران مجاز
- نمایش درست پرسش‌ها و پاسخ‌های پرتکرار
- اجرای موفق برنامه و عبور از بررسی‌های اصلی ساخت و نوع داده، در صورت پیکربندی آن‌ها

برای شروع، آزمون دستی مرحله‌به‌مرحله کافی است؛ اما هرجا امکان دارد آزمون خودکار نیز اضافه شود.

## ۱۲. نقشه راه مرحله‌ای

### مرحله صفر — توافق و آماده‌سازی
- تأیید محدوده نسخه اولیه
- تعیین هماهنگ‌کننده و تقسیم مسئولیت‌ها
- ساخت مخزن GitHub
- تمرین ایجاد شاخه، commit و Pull Request با یک تغییر ساده در مستندات
- توافق بر قواعد محرمانگی و استفاده از داده ساختگی

### مرحله یک — نمونه وب قابل انتشار
- ایجاد پروژه پایه Next.js + TypeScript
- اجرای محلی روی رایانه اعضا
- ساخت یک صفحه ساده معرفی پروژه
- انتشار آزمایشی در Vercel، پس از بررسی دسترسی و شرایط سرویس
- ثبت دستورالعمل اجرای پروژه در README

### مرحله دو — پایگاه داده و دسترسی
- ایجاد پروژه آزمایشی Supabase
- تعریف طرح اولیه داده‌ها
- استفاده از داده‌های ساختگی
- تنظیم احراز هویت و مجوزها در صورت نیاز
- آزمایش اتصال برنامه به پایگاه داده

### مرحله سه — قابلیت‌های اصلی
- فرم و فهرست نوبت‌ها
- بررسی تداخل زمانی
- ثبت اداری اطلاعات حداقلی مراجعان
- ثبت دستی پرداخت‌ها
- گزارش مالی پایه
- آزمون و بازبینی تغییرات اعضا

### مرحله چهار — خدمات هوشمند و کانال‌ها
- شروع چت‌بات با پرسش‌های پرتکرار تأییدشده
- بررسی نیاز واقعی به مدل هوش مصنوعی و هزینه API
- ارزیابی امکان یادآوری نوبت‌ها
- بررسی جداگانه دسترسی و محدودیت‌های تلگرام و اینستاگرام
- طراحی داشبورد بازخورد پس از مشخص‌شدن منبع داده

### مرحله پنج — آماده‌سازی برای استفاده واقعی
- بازبینی امنیت و کنترل دسترسی
- تعریف پشتیبان‌گیری و بازیابی
- آزمون سناریوهای خطا
- بررسی الزامات حقوقی و محرمانگی
- برآورد هزینه نگهداری و پشتیبانی
- تصمیم آگاهانه درباره استفاده عملیاتی یا ادامه در قالب نمونه آموزشی

6. سپس مرحله یک نقشه راه را آغاز کنید.
