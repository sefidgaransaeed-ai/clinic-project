# قرارداد جایگزینی اتمی نوبت — اتصال PR #50

**وضعیت در ۱۸ آبان ۱۴۰۵: PR #51 پس از تأیید مریم ادغام و migration روی پایگاه دادهٔ مشترک اعمال شد. تابع آمادهٔ اتصال است؛ اتصال رابط و آزمون مرورگر هنوز باقی است.**

صاحب دیتابیس و نوع مشترک: سعید. صاحب اتصال Server Action و رابط: مریم.

در «تغییر نام» تقویم، نوبت قبلی لغو و نوبت تازه ساخته می‌شود. دو درخواست جدا
ممکن است پس از لغو اول شکست بخورند و نوبت قبلی از دست برود. تابع زیر این دو
نوشتن را در یک تراکنش انجام می‌دهد. خطا به معنی حفظ نوبت قبلی است.

## قرارداد RPC

`replace_appointment(p_appointment_id, p_patient_id, p_starts_at, p_ends_at, p_requester_mobile, p_note?) → uuid`

| ورودی | معنا |
|---|---|
| `p_appointment_id` | شناسهٔ نوبت قبلی؛ باید تأییدشده و در مهلت ویرایش باشد |
| `p_patient_id` | شناسهٔ مراجع نوبت تازه؛ مراجع پیش از RPC پیدا یا ساخته می‌شود |
| `p_starts_at` و `p_ends_at` | زمان‌های تازه با منطقهٔ زمانی؛ همان خروجی معتبر ثبت دستی |
| `p_requester_mobile` | شمارهٔ تماس این نوبت؛ ۱۱ رقم انگلیسی با شروع ۰۹ |
| `p_note` | توضیح اختیاری؛ رشتهٔ خالی به `null` تبدیل می‌شود |

خروجی، شناسهٔ نوبت تازه است. نوبت قبلی با `cancelled/cancelled` حفظ می‌شود؛
نام و شمارهٔ درخواست قدیمی، سایر مشخصاتش و پرداخت‌های متصل به آن عوض نمی‌شوند.
نوبت تازه `source=panel` دارد. نام مراجع از `patients`، مطب از `clinic_for_moment`
و `created_by` از نشست کاربر تعیین می‌شوند.

تابع `SECURITY INVOKER` است: RLS، قید هم‌پوشانی و قفل مهلت ویرایش اعمال می‌شوند.
فقط `authenticated` اجازهٔ اجرا دارد و داخل تابع نیز نقش پزشک/منشی و فعال‌بودن
پروفایل بررسی می‌شود. با `createClient()` و نشست کاربر صدا زده شود، نه `admin.ts`.

### پاسخ به نکته‌های بازبینی PR #51

- ساعت کاری و تعطیلی طبق A-2/A-6 در برنامه کنترل می‌شوند؛ ثبت خارج از برنامه نیازمند
  هشدار مشخص و تأیید دوم است. گام ۱۵ دقیقه در برنامه اجباری است و استثنا ندارد.
  RPC این قواعد رابط را دوباره اجرا نمی‌کند؛ فراخوانی مستقیم توسط کاربر مجاز پنل
  از آن‌ها عبور می‌کند. این محدودیت قرارداد فعلی است، نه تضمین کنترل گام در دیتابیس.
- مطب از زمان جدید محاسبه می‌شود. طبق [تصمیم 0011](decisions/0011-two-clinics.md)،
  `clinic_for_moment` بیرون از ساعت کاری `null` برمی‌گرداند؛ رابط باید نتیجه و هشدار
  مربوط را نشان دهد. تابع خودش هشدار تعاملی ندارد.
- رمز اتصال رانر از آرگومان `--remote` حذف شد و فقط در محیط فرایند فرزند، با
  `PGPASSWORD`، قرار می‌گیرد. این کار دیده‌شدن رمز در فهرست آرگومان پردازه‌ها را رفع
  می‌کند؛ محیط پردازه همچنان راز است و نباید در گزارش اشکال چاپ شود.

## تغییر لازم در کد مریم

پیش‌نیاز دیتابیس انجام شده است. مریم پس از همگام‌سازی شاخه با `main`:

1. `requireRole`، اعتبارسنجی زمان و شماره، هشدار/تأیید دوم A-6 و پیدا/ساخت مراجع حفظ شوند.
2. در `renameAppointment`، زنجیرهٔ لغو ← درج ← تلاش برای برگرداندن حذف و با یک RPC جایگزین شود:

```ts
const { data: appointmentId, error } = await supabase.rpc("replace_appointment", {
  p_appointment_id: oldAppointmentId,
  p_patient_id: prepared.row.patient_id!,
  p_starts_at: prepared.row.starts_at,
  p_ends_at: prepared.row.ends_at,
  p_requester_mobile: prepared.row.requester_mobile,
  p_note: prepared.row.note ?? undefined,
});
```

3. در خطا، هیچ لغو یا بازگرداندن دیگری اجرا نشود. در موفقیت، پیام و تازه‌کردن صفحه مثل قبل باشد.
4. نوع RPC در `src/lib/database.types.ts` اضافه شده؛ برای این تابع cast لازم نیست.

این تراکنش فقط دو نوشتنِ نوبت را پوشش می‌دهد. اگر مراجع تازه پیش از RPC ساخته شده
باشد و RPC شکست بخورد، آن مراجع باقی می‌ماند؛ تابع نه مراجع و نه پرداخت را حذف نمی‌کند.

| کد خطا | رفتار رابط |
|---|---|
| `23P01` | پیام فعلی هم‌پوشانی ثبت دستی؛ نوبت قبلی محفوظ است |
| `55000` | نوبت دیگر تأییدشده نیست؛ پیام فارسی تابع و تازه‌کردن صفحه |
| `P0002` | نوبت یا مراجع پیدا نشده؛ پیام فارسی تابع |
| `P0001` | قفل مهلت ویرایش؛ پیام فعلی مربوط به مهلت |
| `22023` | ورودی نامعتبر؛ پیام فارسی تابع |
| `42501` | دسترسی مجاز نیست؛ پیام فارسی ثابت دسترسی |
| سایر کدها | پیام عمومی شکست ثبت؛ جزئیات فنی به کاربر نشان داده نشود |

`mapDbError` فعلی PR #50 برای `55000`، `P0002` و `22023` نگاشت مشخص ندارد؛
این سه مورد در اتصال بالا اضافه شوند. نقص ذخیرهٔ تاریخ تولد/جنس، اصلاح جداگانهٔ مریم است.

## آزمون و انتشار

آزمون SQL در `supabase/tests/replace_appointment.sql` با دادهٔ ساختگی اجرا می‌شود.
رانر `supabase/tests/run-replace-appointment.mjs` خود migration و تمام داده‌های آزمون
را در یک تراکنش اجرا می‌کند و در پایان عمداً rollback می‌کند؛ آزمون به معنی انتشار نیست.

```powershell
node --env-file=.env.local supabase/tests/run-replace-appointment.mjs --cli <path-to-supabase.exe>
```

گزینهٔ `--check` فقط اتصال را با یک پرس‌وجوی خواندنی می‌سنجد. رانر مقدار اتصال را چاپ نمی‌کند
و رمز را داخل آرگومان‌های ابزار Supabase قرار نمی‌دهد.

نتیجهٔ بررسی در ۱۷ آبان ۱۴۰۵:

- ۱۳ آزمون روی PostgreSQL با نقش‌ها و داده‌های ساختگی گذشتند؛ migration و داده‌های
  آزمون همگی با خطای عمدی پایانی بازگردانده شدند.
- ثبت موفق پزشک/منشی، حفظ پرداخت قبلی، بازگردانی کامل نوبت هنگام خطای هم‌پوشانی،
  رد استفادهٔ دوباره از نوبت قبلی و کنترل مهلت و دسترسی بررسی شدند.
- `npm run build`، `npm run lint` و بررسی نحو رانر موفق بودند.
- استفادهٔ دوباره به‌صورت پشت‌سرهم آزموده شد؛ رقابت واقعی دو نشست هم‌زمان و اتصال
  مرورگر هنوز آزموده نشده‌اند و باید پس از اتصال رابط انجام شوند.

بررسی پس از نصب در ۱۸ آبان: بدنهٔ تابع با migration بازبینی‌شده یکی است؛ مجوز اجرا
برای `authenticated` برقرار و برای `anon` و `service_role` بسته است. هر ۱۳ آزمون با
رانر اصلاح‌شده گذشت و همهٔ داده‌های آزمون بازگردانده شد. فهرست migrationهای مشترک
تا شمارهٔ ۱۳ همگام است.

مریم اتصال بالا را انجام می‌دهد و دو نشست جدا را می‌آزماید: تلاش برای جایگزینی یک نوبت
نباید دو نوبت تازه بسازد؛ شکست به‌علت هم‌پوشانی نباید نوبت قبلی را لغو کند.
