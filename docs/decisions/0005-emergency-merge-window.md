# 0005 — پنجرهٔ ۲۴ ساعته برای ادغام اضطراری

- **تاریخ:** ۲۹ مهر ۱۴۰۵
- **وضعیت:** تأییدشده
- **تغییر می‌دهد:** قاعدهٔ `protect-main` که در تصمیم‌های اولیه «بدون استثنا حتی برای مدیر» ثبت شده بود

## زمینه

در ۲۹ مهر، **۹ PR باز** بود و روی هیچ‌کدام حتی یک بازبینی ثبت نشده بود. شاخهٔ `main` هنوز فقط commit اول را داشت.

دلیلش فنی نبود:

| نفر | می‌تواند تأیید کند؟ |
|---|---|
| نفر اول (سعید) | ❌ نویسندهٔ همهٔ PRهاست — GitHub اجازه نمی‌دهد کسی PR خودش را تأیید کند |
| **مریم** | ✅ **تنها نفر** |
| هستی | ❌ دعوت GitHub را نپذیرفته |

یعنی کل پروژه به **یک نفر** گره خورده بود، با **۱۹ روز** تا تحویل ۱۸ آبان، در حالی که تحلیل مسیر بحرانی (تصمیم `0004`) نشان داده بود حدود ۲۹ ساعت از کار دو عضو دیگر پشت همین ادغام‌ها ایستاده است.

## تصمیم

**نقش `admin` مخزن به فهرست عبور (`bypass_actors`) قاعدهٔ `protect-main` اضافه می‌شود، با حالت `pull_request`.**

### قاعدهٔ مکتوب استفاده

| شرط | مقدار |
|---|---|
| مهلت | **۲۴ ساعت** از لحظهٔ باز شدن PR |
| دامنه | فقط **PR مسدودکننده** |
| ثبت | هر بار استفاده، در کامنت همان PR با ذکر دلیل نوشته شود |

**تعریف عینی «PR مسدودکننده»:** PRای که کار شخص دیگری به آن وابسته است. طبق گراف وابستگی پنل، الان یعنی PRهای مربوط به `p1-04` و `p1-07`.

### چرا `pull_request` و نه `always`

حالت `pull_request` یعنی مدیر فقط می‌تواند **PR را بدون تأیید ادغام کند**. این سه محافظت دست‌نخورده می‌مانند:

- ❌ پوش مستقیم روی `main` همچنان ممنوع
- ❌ `force push` همچنان ممنوع
- ❌ حذف شاخه همچنان ممنوع

## ⚠️ آنچه این تصمیم **اجرا نمی‌کند**

**«۲۴ ساعت» و «فقط مسدودکننده‌ها» را هیچ چیز فنی اجرا نمی‌کند.**

تنظیمات GitHub فقط دو حالت دارد: مدیر یا می‌تواند عبور کند یا نمی‌تواند. هیچ تنظیمی برای «فقط بعد از ۲۴ ساعت» یا «فقط اگر مسدودکننده باشد» وجود ندارد — این‌ها در هیچ‌کدام از هشت پارامتر قاعدهٔ PR نیستند.

از لحظهٔ اعمال، مدیر می‌تواند **هر PRای را هر وقت** ادغام کند. آنچه این دو شرط را نگه می‌دارد:

| ✅ هست | ❌ نیست |
|---|---|
| GitHub ثبت می‌کند چه کسی و کِی ادغام کرد | جلوگیری در لحظه |
| لاگ عبور از قاعده (`rule-suites`) خودکار پر می‌شود | بررسی گذشتن ۲۴ ساعت |
| بازبینی پس از واقعه ممکن است | بررسی مسدودکننده بودن |

**این در سند نوشته شده تا بعداً کسی فکر نکند قاعده فنی اجرا می‌شود.**

## دو PR که عمداً مشمول نمی‌شوند

| PR | چرا |
|---|---|
| **مدل داده** | تعریف کار `p1-07` صریح می‌گوید بازبینی نفر دوم (نوبت‌ها و مراجعان) و نفر سوم (مالی و بازخورد) بخشی از خود کار است. مدل داده قراردادی است که هر صفحه و هر جدول رویش ساخته می‌شود |
| **معیار پذیرش** | همان دلیل — ارزش این سند **در بازبینی** است، نه در وجودش |

این دو منتظر بازبینی واقعی مریم و هستی می‌مانند، حتی اگر از ۲۴ ساعت بگذرد.

## گره‌ای که این تصمیم حل **نمی‌کند**

`bypass` فقط به **مدیر** اجازهٔ ادغام می‌دهد.

| چه کسی در دسترس نباشد | نتیجه |
|---|---|
| مریم | ✅ کار جلو می‌رود |
| **نفر اول** | ❌ **همان بن‌بست، فقط جای آدمش عوض شده** |

نفر اول صریح گفت ممکن است چند روز نتواند وقت بگذارد. **این تصمیم آن حالت را پوشش نمی‌دهد.**

**تنها راهی که هر دو حالت را پوشش می‌دهد:** هستی دعوت GitHub را بپذیرد تا دو تأییدکنندهٔ مستقل از نویسنده وجود داشته باشد. دعوتش **۲۶ اکتبر ۲۰۲۶** منقضی می‌شود.

## پیامد

- قاعدهٔ «بدون استثنا حتی برای مدیر» دیگر برقرار نیست و این سند مرجع جدید است.
- تیم باید بداند: اگر مریم در ۲۴ ساعت PR مسدودکننده‌ای را نبیند، بدون او ادغام می‌شود. **بهتر است از قبل بداند، نه اینکه بعداً بفهمد.**
- اگر استفاده از این استثنا از نادر به عادی تبدیل شد، یعنی مشکل جای دیگری است — کمبود تأییدکننده، نه کندی بازبینی — و باید دوباره تصمیم گرفت.

## راه بازگشت

برگرداندن `bypass_actors` به فهرست خالی. یک تغییر در همان صفحهٔ تنظیمات، لحظه‌ای.
