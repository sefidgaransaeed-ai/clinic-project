هوشمندسازی مطب پزشک متخصص طب فیزیکی و توان‌بخشی

سامانه‌ای یکپارچه و مرحله‌ای برای پشتیبانی از امور اجرایی، نوبت‌دهی و مالی مطب که تیم با رویکرد آموزشی و به کمک ابزارهای هوش مصنوعی (Vibe Coding) آن را می‌سازد.

نسخه ۰.۵ وضعیت: آماده شروع اجرا تحویل: ۱۸ آبان ۱۴۰۵ به‌روزشده: ۲۶ مهر ۱۴۰۵
نکته مهم: تصمیم‌های ساختاری گرفته شده و کار اجرایی از ۲۶ مهر آغاز می‌شود. برنامه روزبه‌روز هر نفر در فایل جداگانه «راهنمای اجرایی» آمده است و این سند مرجع تصمیم‌هاست.

خلاصه در یک نگاه: کل پروژه، شامل سایت، درخواست نوبت آنلاین، پنل پزشک و منشی (نوبت‌ها، مراجعان، امور مالی، تنظیمات و کاربران) و خدمات مرحله ۴ (چت‌بات پرسش‌های پرتکرار، ربات پیام‌رسان و یادآوری، نظرسنجی و داشبورد بازخورد)، باید تا ۱۸ آبان ۱۴۰۵ با داده ساختگی روی Vercel تحویل شود. پرونده پزشکی و اطلاعات بالینی در محدوده پروژه نیست. پشته فنی Next.js، Supabase، Vercel و GitHub است و تیم سه‌نفره با نقش‌های «نفر اول» (هماهنگ‌کننده، سعید سفیدگران)، «نفر دوم» و «نفر سوم» کار می‌کند. از ۲۲ مورد تصمیم، ۱۹ مورد تعیین شده و ۳ مورد باز است.
تغییرات نسخه ۰.۵ (۲۶ مهر ۱۴۰۵):
  • ساخت سایت عمومی (صفحه‌ها، تنظیمات پرسش‌های پرتکرار و اطلاعات سایت، دکمه‌های واتس‌اپ و اینستاگرام) از نفر اول به نفر سوم منتقل شد.
  • پنل مشترک مدیریت پروژه راه‌اندازی شد: هر عضو وضعیت کارهایش را در آن ثبت می‌کند و مدیر پروژه پیشرفت واقعی در برابر برنامه، عقب‌افتادگی‌ها و موانع را می‌بیند. پنل پروژه
تغییرات نسخه ۰.۴ (۲۶ مهر ۱۴۰۵):
  • دامنه تحویل «کل پروژه» و تاریخ تحویل ۱۸ آبان ۱۴۰۵ تعیین شد و نقشه راه تاریخ‌دار شد.
  • «پنل پزشک و منشی» (همان پنل مدیریت) به‌عنوان یک بخش مستقل با نقشه صفحه‌ها تعریف شد؛ شامل تنظیمات (ساعات کاری و مدت نوبت، تعطیلات و مرخصی، پرسش‌های پرتکرار و اطلاعات سایت، بیمه‌ها و روش‌های پرداخت) و مدیریت کاربران توسط پزشک.
  • تقسیم کار با سه نقش نفر اول، دوم و سوم و قواعد همکاری از پیشنهاد یکی از اعضا ادغام شد؛ کار نفر دوم و سوم با داده ساختگی موازی با مرحله ۲ شروع می‌شود.
  • بسته «ب» به «امور مالی» تغییر نام داد و کارهای مرحله ۴ بین بسته‌ها تقسیم شد.
  • منبع بازخورد فقط نظرسنجی خود سامانه است.
  • برای واتس‌اپ و اینستاگرام «تلاش برای اجرا» تصمیم گرفته شد؛ بررسی اولیه نشان داد API رسمی هر دو برای کسب‌وکار مستقر در ایران مجاز نیست. جایگزین‌ها و گزارش امکان‌سنجی در بخش ۳ آمده است.
  • پیوست «نوع هر عملیات» (ورک‌فلو، اتوماسیون، چت‌بات یا ایجنت) اضافه شد.

هدف پروژه

طراحی و پیاده‌سازی تدریجی یک سامانه یکپارچه برای پشتیبانی از امور اجرایی و مالی یک مطب پزشک متخصص طب فیزیکی و توان‌بخشی، با رویکرد آموزشی و استفاده از ابزارهای هوش مصنوعی برای کمک به توسعه نرم‌افزار (Vibe Coding).

تمرکز نسخه اولیه بر امور اداری، نوبت‌دهی و مالی است؛ نه نگهداری یا پردازش پرونده پزشکی و اطلاعات بالینی بیماران.

بر اساس اطلاعات مطرح‌شده تا این مرحله:

آنچه می‌دانیم

  • مطب در ایران فعالیت می‌کند.
  • تعداد مراجعه‌ها کمتر از ۲۰ مراجعه در روز است.
  • نوبت‌دهی و ارتباط با مراجعان از راه‌هایی مانند تلفن، مراجعه حضوری و پیام‌رسان‌ها انجام می‌شود.
  • اطلاعات در دفترها و فایل‌های مختلف ثبت می‌شوند و نرم‌افزار یکپارچه‌ای برای مطب وجود ندارد.
  • هدف، یکپارچه‌سازی تدریجی امور اجرایی مطب است.
  • اطلاعات پرداخت در مرحله اول می‌تواند به‌صورت دستی ثبت شود و سپس برای تهیه گزارش‌های مالی استفاده شود.
  • جدید ساعات کاری مطب ظفر: شنبه و چهارشنبه، ۱۱ تا ۱۷؛ مدت هر نوبت ۱۵ دقیقه.

آنچه پیش‌تر روشن نبود

  • دسترسی به داده‌های بازخورد و نظرات مراجعان هنوز مشخص نشده بود.
    تعیین شد: فرم نظرسنجی در سامانه و نظرات سایت‌های نوبت‌دهی.
  • ترکیب دقیق کانال‌های ارتباطی هنوز نهایی نشده بود.
    تعیین شد: اولویت با واتس‌اپ، تلگرام و اینستاگرام.

۷. ربات پیام‌رسان، واتس‌اپ و اینستاگرام

  • کانال‌های اولویت‌دار: واتس‌اپ، تلگرام، اینستاگرام
  • تلگرام: API ربات رایگان است؛ ربات به پرسش‌های پرتکرار پاسخ می‌دهد و یادآوری می‌فرستد. تلگرام در ایران فیلتر است و مراجعان بدون دسترسی آزاد آن را نمی‌بینند
  • پیشنهاد جایگزین: پیام‌رسان «بله» API ربات مشابه تلگرام دارد (فرض — نیازمند تأیید با مستندات رسمی بله) و با همان کد قابل اتصال است
  • واتس‌اپ و اینستاگرام (تلاش برای اجرا): طبق مستندات Meta، کسب‌وکارهای مستقر در ایران مجاز به استفاده از WhatsApp Business Platform نیستند و کاربران در ایران پیام آن را دریافت نمی‌کنند؛ شرایط تجاری Meta هم فعالیت تجاری از کشورهای تحت تحریم آمریکا را محدود می‌کند. بنابراین مسیر API رسمی بسته است و دور زدن آن (مثلاً ثبت کسب‌وکار به نام کشور دیگر) در برنامه نیست
  • آنچه ساخته می‌شود: دکمه گفتگو در واتس‌اپ (لینک wa.me) و لینک صفحه اینستاگرام در سایت، به‌علاوه گزارش امکان‌سنجی مستند

پنل پزشک و منشی (همان پنل مدیریت) مصوب

قواعد تقسیم کار مصوب

  1. قرارداد داده اول: تا تأیید docs/data-model.md کسی جدول یا صفحه متصل به پایگاه داده نمی‌سازد.
  2. بخش مشترک یک صاحب دارد: پایگاه داده، ورود، نقش‌ها و پوسته پنل را فقط نفر اول می‌سازد؛ بقیه پیش از ادغام آن با داده ساختگی کار می‌کنند.
  3. جدول یا ستون جدید فقط از مسیر نفر اول: بقیه درخواست را در گروه می‌نویسند و منتظر ادغام می‌مانند.
  4. فایل‌های مشترک فقط دست نفر اول است: چیدمان، منو، package.json و نوع‌های داده مشترک.
  5. ارتباط ماژول‌ها یک‌طرفه: پرداخت فقط به شناسه نوبت اشاره می‌کند و خود نوبت را تغییر نمی‌دهد.
  6. هر شاخه یک کار و یک ماژول: PR کوچک باشد و هر روز پیش از شروع، آخرین main گرفته شود.
  7. قبل از هر PR: اجرای npm run build، بررسی نوع داده و آزمون‌های مربوط.
  8. بازبینی متقابل: PRهای نفر اول را هم یکی از دو عضو دیگر بازبینی می‌کند.
  9. جلسه ۱۰ دقیقه‌ای: شنبه، دوشنبه و چهارشنبه؛ چه کردم، چه می‌کنم، به چه نیاز دارم.

واژه‌نامه برای اعضای غیرفنی

Vibe Coding
توسعه نرم‌افزار با توصیف خواسته‌ها به زبان طبیعی و کمک گرفتن از هوش مصنوعی برای نوشتن کد
Claude Code
دستیار هوش مصنوعی که روی رایانه هر عضو اجرا می‌شود و در نوشتن، توضیح و اصلاح کد کمک می‌کند
GitHub / Repository
بستر آنلاین نگهداری کد؛ «مخزن» محل مشترک همه فایل‌های پروژه است
Branch
شاخه؛ نسخه‌ای جدا از کد که هر عضو روی آن کار می‌کند تا نسخه اصلی دست‌نخورده بماند
main
شاخه اصلی و پایدار پروژه که فقط تغییرات بازبینی‌شده وارد آن می‌شوند
Commit
ثبت یک مجموعه تغییر با پیامی که توضیح می‌دهد چه چیزی عوض شده است
Pull Request (PR)
درخواست ادغام تغییرات یک شاخه در شاخه اصلی، که پیش از ادغام بازبینی می‌شود
Merge
ادغام تغییرات یک شاخه در شاخه دیگر
Next.js / TypeScript
چارچوب ساخت وب‌سایت و برنامه وب، همراه با زبانی که خطاهای نوع داده را زودتر نشان می‌دهد
Supabase / PostgreSQL
سرویس آنلاین پایگاه داده رابطه‌ای همراه با امکانات ورود کاربران
Vercel
سرویس میزبانی و انتشار آنلاین برنامه‌های وب
Auth
احراز هویت؛ سازوکار ورود کاربران و تعیین اینکه هر کس به چه چیزی دسترسی دارد
RLS
قفل سطح ردیف؛ قاعده‌ای در خود پایگاه داده که مشخص می‌کند هر کاربر فقط کدام ردیف‌ها را ببیند یا تغییر دهد
API
درگاهی که یک سرویس از طریق آن به برنامه‌های دیگر خدمت می‌دهد (مثل ارسال پیامک)
.env
فایل محلی نگهداری کلیدها و رمزها که هرگز نباید در مخزن قرار گیرد
Microservices
شکستن سامانه به چند سرویس مستقل؛ برای شروع این پروژه توصیه نمی‌شود
یادآوری: این سند جمع‌بندی تصمیم‌ها و پیشنهادهای مطرح‌شده تا این مرحله است؛ نه مشخصات نهایی محصول و نه تأییدیه امنیتی یا حقوقی برای استفاده عملیاتی.
